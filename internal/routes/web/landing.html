The part nobody budgets for

You did not set out to build an invitation system.

Every B2B product arrives at the same six months of work before it can charge anyone. It is all undifferentiated, all load-bearing, and all of it fails quietly.

  1. 01

    One missing predicate is a breach

    Isolation lives in whichever WHERE clause the last developer remembered. The query that forgets is indistinguishable from the query that works — until it is in a customer's export.

  2. 02

    Roles calcify into if-statements

    Permissions start as three constants in middleware. By the time a customer asks for a read-only auditor, changing who can do what means a deploy.

  3. 03

    Machine access is an afterthought

    API keys get bolted on with the permissions of whoever made them, so a key silently gains power when its owner is promoted and keeps it after they leave.

  4. 04

    The audit log arrives too late

    It gets written the week the first security questionnaire lands, on a table the application can still UPDATE — which is the one property an auditor asks about.

Isolation model

One request, three independent boundaries

Pick a tenant, send the same request, and watch where the boundary is actually applied. The query below carries no tenant predicate at all — the database adds it.

  1. Request ID assigned GET /api/v1/projects
  2. Credential verified Bearer eyJhbGciOi…
  3. Tenant taken from the credential tenant_id = …
  4. Permission gate project:view — granted by role
  5. Scoped transaction opened SET LOCAL app.tenant_id = …
  6. Row-level security filters the result — rows returned

An illustration of the real middleware chain and policy, with sample rows. The mechanism is not simulated: it is pkg/txscope plus a FORCE ROW LEVEL SECURITY policy on every tenant-scoped table.

Architecture

Four layers, one direction of travel

Handlers never touch the database. Repositories never make authorization decisions. Every tenant-scoped read and write goes through a single path, which is why the guarantee holds.

  1. Edge

    Middleware chain

    Request ID, structured logging, panic recovery, security headers, CORS, then the credential. Rate limited per IP before authentication.

    RequestID Logger Recovery Headers Auth Permission gate
  2. Domain

    Twelve self-contained modules

    Each one is the same four files: entity, repository, service, handler. A module can be read in an afternoon and deleted without archaeology.

    identity authz teams projects invitations apikeys billing audit
  3. Scope

    One path to the database

    txscope opens a transaction and sets app.tenant_id. SET LOCAL semantics mean the value cannot outlive it or leak across a pooled connection.

    BEGIN set_config('app.tenant_id') query COMMIT
  4. Data

    PostgreSQL, with the policy on

    Every tenant-scoped table is ENABLE and FORCE ROW LEVEL SECURITY, so the policy applies even to the table owner. The runtime role is NOSUPERUSER NOBYPASSRLS.

    RLS policy CITEXT JSONB triggers append-only audit

What is already finished

Complete on the first day, not scaffolded

Each capability is wired end to end — SQL schema, service rules, HTTP surface, and a screen in the workspace.

  • Authentication that survives a stolen token

    Password login, refresh-token rotation with reuse detection, password reset, email verification, and Google or GitHub OAuth. Changing a password revokes every refresh token for that user.

    • Rotating refresh families
    • bcrypt at rest
    • OAuth state signed with HMAC

  • Roles you can edit at runtime

    Five roles and 21 permissions seeded per tenant. Checks resolve from the database on every request, so a change applies without a deploy.

  • Keys that authorize themselves

    Scoped machine credentials, hashed at rest, revocable. A key authorizes from its own scopes, never from its creator's current role — and cannot be granted role or org management at all.

  • Teams, members, invitations

    Single-use hashed invite tokens, redeemable without a prior account, accepted in one atomic database function.

  • Quotas enforced at the point of use

    Seat and project limits are checked before the write is allowed, not reported on a dashboard afterwards.

  • An audit trail a compromised credential cannot edit

    audit_logs is append-only in the strongest available sense: the application role holds no UPDATE or DELETE grant on it, so erasing the trail is not a permission the running process has to lose — it never had it.

    • Separate product-facing timeline
    • Secrets never written to entries
    • Actor, IP and user agent captured

Enterprise security

Guarantees, not intentions

Each of these is a mechanism with a failure mode, chosen over a convention with a code review.

Runtime role
The app cannot bypass its own policies. It connects as a NOSUPERUSER NOBYPASSRLS role, because a superuser ignores row-level security entirely and would make the isolation tests pass for the wrong reason.
Tenant source
A header cannot choose your tenant. Tenant identity comes only from a verified credential. A pre-auth header or subdomain that contradicts it is rejected with TENANT_MISMATCH.
Pre-tenant lookups
The three unavoidable ones are narrowed, not excused. Invite tokens, API keys and login-by-email cannot know the tenant in advance, so each is a scoped SECURITY DEFINER function doing one indexed match on a 256-bit secret.
Secret handling
Shown once, stored as a hash. Secrets never reach an audit entry or a log line. Request logs omit bodies, query strings and the Authorization header entirely.
Browser surface
Locked down as tightly as the API. A strict Content-Security-Policy, frame denial, nosniff, referrer and permissions policy on every response. HSTS over TLS. CORS is off by default and has no wildcard mode, since responses carry credentials.

// Every tenant-scoped read goes through txscope, which is the
// only place app.tenant_id is ever set.
func (r *Repository) List(ctx context.Context) ([]Project, error) {
    var out []Project
    err := txscope.WithTenantTx(ctx, r.db, func(tx *gorm.DB) error {
        // No tenant predicate. The policy adds it.
        return tx.Where("deleted_at IS NULL").Find(&out).Error
    })
    return out, err
}

FAQ

The questions a reviewer asks

Is row-level security not a performance problem?

The policy compiles into the query plan as an ordinary predicate on an indexed column, which is the same work the hand-written WHERE tenant_id was doing. What it removes is the case where a developer forgets it. The cost that does exist is one set_config per transaction.

What happens on managed Postgres, where I own the tables?

A table owner normally bypasses its own policies, which would silently disable isolation on exactly that kind of deployment. Every tenant-scoped table is therefore declared FORCE ROW LEVEL SECURITY, which applies the policy to the owner too. A new tenant-scoped table needs both ENABLE and FORCE.

Can an API key escalate its own privileges?

No. A key authorizes purely from its own scope list; its creator is recorded for attribution and never consulted for authority. role:manage and org:manage cannot be granted to a key at all, and keys are blocked from minting keys or changing passwords.

Why is there no email being sent yet?

Invitation, reset and verification tokens are published as domain events, but no transport is wired up — so this is stated plainly rather than implied. Until one is, the dashboard surfaces a new invite link directly so the flow is usable. Kafka publishing, Redis caching and S3 uploads are the same shape: interfaces that degrade to no-ops.

How is the frontend built?

It is not built. There is no bundler, no framework and no runtime dependency: the dashboard is embedded in the binary and served from the same origin as the API, which is why there is no CORS configuration to get wrong. Every DOM node is created through a helper that assigns text via textContent, so tenant-supplied names cannot become stored XSS.

What is deliberately not here?

Email delivery, event publishing, caching and file storage, as above. Two-factor authentication is schema-ready but not implemented. There is no billing provider integration — the plan catalog and quota enforcement are real, the card is not.
